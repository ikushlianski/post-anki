# Mac app second review (unreviewed shared files and wave 3/4)

Scope read in full: TopicStudyScreen, LearningListItemModel, DomainNodeScreen, all Shared *Sheet files, Admin*, DuplicateReview*, DomainMapModel, Practice/PhraseBank/WritingCheck models, and PostAnkiMac Authoring, LanguageAdmin, Structure, Launch. No Critical findings. No try!, fatalError or as! in scope.

1. High: Subject switch on Knowledge maps can show the wrong subject's map. Sources/Shared/DomainMapModel.swift:26 and :64-68; Sources/PostAnkiMac/Structure/MacKnowledgeMapsView.swift:36-44. select() sets the new subjectId and empties the tree, then load() returns early because the guard sees an in-flight load (the Picker is enabled as soon as subjects arrive, before the first map returns, and also during any earlier switch). The in-flight load then writes the OLD subject's tree (it holds a local copy of the id), and the Priority, Document scan and Recommendation tools open with the new subjectId and the old tree's names. Fix: disable the Picker while isLoading, or make select() cancel/await the running load and re-run for the latest subjectId (discard results whose subjectId no longer matches).

2. Medium: Offline or signed-out error is hidden after switching subject. MacKnowledgeMapsView.swift:79 and :100. After select() the tree is empty and hasLoaded is true, so the view takes the "No map for this subject yet" branch; the error banner exists only in the non-empty branch. A failed switch reads as an empty map. Fix: when errorMessage is set and the tree is empty, show MacLoadStateView with model.failureKind (or render the banner on the empty-state branch too).

3. Medium: Language practice can land on an empty screen or a stale error. Sources/Shared/PracticeModel.swift:48-63 and :81; MacLanguagePracticeView.swift:63-77. (a) loadSettings() never clears errorMessage, so after one failed start, a successful retry via start() sees errorMessage != nil and skips nextBatch(): the screen shows settings, an old error and no phrases. (b) The batch call is a slow AI request; clicking Phrase bank or Check my writing in the toolbar cancels the .task, URLSession throws URLError.cancelled (not CancellationError), the model records an "offline" error, and start() will not run again because settings is already set. Fix: reset errorMessage/failureKind at the top of loadSettings(); in nextBatch/loadSettings treat ProgressLoadError.from(error) == nil as cancellation and return without an error; let start() generate a batch when phrases is empty.

4. Medium: Save failures in modal sheets look like "nothing happened". Sources/Shared/AddGapSheet.swift:44, SubjectManageSheets.swift:40 and :87, CourseEditSheets.swift:25 and :87, TopicTagSection.swift:19-22, :58 and :117. These sheets get only a Bool back; the error text is written to the parent model (TopicGapsModel.errorMessage, SubjectManageModel.errorMessage, CourseEditModel.errorMessage, TopicTagModel.message) and rendered behind the modal sheet, which stays open. A tag picker that cannot load tags also shows a blank list with no message. Fix: have the callbacks return an optional message (as QuestionVariantEditSheet does) and show it inside the sheet, or render the model's error inside the sheet.

5. Medium: A reload that fails after a first success is invisible on four Mac screens, so stale data looks current when offline or signed out. MacRefocusView.swift:26-71 (list shows only notice), MacAdminView.swift:105-116, MacLanguagePracticeView.swift:22-40, MacPhraseBankView.swift:61-95. Each switches to MacLoadStateView only while !hasLoaded (or bank == nil); afterwards the model's errorMessage is never rendered, unlike MacCourseBuildsView, MacDuplicatesView and MacSubjectsView which use MacLibraryErrorBanner. Fix: add MacLibraryErrorBanner(message: model.errorMessage) above the content on these screens.

6. Medium: "catch is CancellationError" does not catch URLSession cancellation, so a cancelled load is shown as an error. URLSession throws URLError(.cancelled); only ProgressLoadError.from(error) == nil covers both (TopicGapsModel.load does it right). Wrong pattern at AdminModel.swift:34, DomainMapModel.swift:56, DuplicateReviewModel.swift:41, SubjectManageModel.swift:63, CourseRefocusScreen.swift:25, CourseBuildListScreen.swift:24, PracticeSubjectsScreen.swift:24, PhraseBankScreen.swift:27, WritingCheckModel.swift:35, PracticeModel.swift:81. TopicStudyScreen.swift:16-27 (TopicNotesModel.load) has no handling at all, and StudyToolsError.message maps URLError.cancelled to "You appear to be offline", which pull-to-refresh or pushing a screen over a loading one triggers. Fix: replace with `catch where ProgressLoadError.from(error) == nil { return }` (clear isLoading via defer) in each, and add it to TopicNotesModel.

7. Medium: Writing check "Try again" does nothing useful. Sources/Shared/WritingCheckModel.swift:27-40; MacWritingCheckView.swift:36-39. Retry calls loadHistory(), which never clears errorMessage, so the red error stays after a successful reload; and when the failed action was check() the user's text is not resubmitted. Fix: clear errorMessage at the start of loadHistory(); keep the error kind (check vs history) and retry the matching call.

8. Medium: Admin scan failures are misleading and invite a paid re-run. Sources/Shared/AdminModel.swift:51-67; Packages/PostAnkiAPI/Sources/PostAnkiAPI/APIClient+Admin.swift:18; APIClient.swift request() uses URLSession.shared. Scans are synchronous POSTs to paid AI endpoints; the default 60 s idle timeout fires on a long scan, the table shows "Scan failed." while the server keeps running, and the Run button re-enables. Offline and signed-out also show the same text (only 403 gets a reason). Assumption: scan durations were not measured. Fix: give scan requests a longer timeout, map URLError.timedOut to "Still running or timed out; check before running again", and map 401/offline to the usual messages.

9. Medium: The subject-merge confirmation is attached to the ForEach, so every row owns a dialog bound to the same state. Sources/Shared/SubjectDuplicateList.swift:41-51 (inside MacDuplicatesView's List). SwiftUI applies the modifier per row; presentation is unreliable (duplicates, none, or lost when the row scrolls out) and the merge, which deletes a subject, depends on it. Hypothesis from SwiftUI behavior, not reproduced. Fix: move .confirmationDialog to the enclosing container, or use macConfirmDestructive (which uses presenting:) on MacDuplicatesView.
