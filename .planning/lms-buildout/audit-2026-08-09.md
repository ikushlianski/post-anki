## Blocking finding — the fold-in path has no implementation

The learning list's stated default for a single article is to fold it into the existing taxonomy
rather than spawn a mini-course. The recommender produces that verdict correctly
(`packages/core/src/learning-list/recommend-destination.ts:15` returns `fold_in`).

The approval path then rejects it. `learning-list-approval.orchestrator.ts:52-58` accepts only
`mini_course` and `extend_curriculum`; anything else returns `not_awaiting_decision`. The string
`folded_in` appears exactly once in the whole API — as a return value at
`learning-list-classification.orchestrator.ts:162` — and nothing consumes it.

So: paste a single article, the system correctly recommends folding it into an Area, and there is
no way to accept that recommendation. The most common intake case is a dead end.

Underlying design fork, unresolved: `topics.curriculum_id` is NOT NULL
(`apps/api/src/db/schema.ts:294`), so a folded-in topic needs a curriculum to live under — but the
entire point of folding in is not creating a course. Either an implicit per-Area container is
introduced, or topics must be allowed to hang off a domain node directly. Not decidable silently.
