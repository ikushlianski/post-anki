# Root A report — AI Q&A backend (Phases 1–3)

## What shipped

A new app-wide Q&A endpoint `POST /qa-chat` backed by a tool-calling Mastra agent,
plus two read-only tools. Root B (apps/web) consumes this endpoint; nothing under
apps/web was touched.

### Endpoint contract (for root B)

`POST /qa-chat`, JSON body:

```json
{
  "message": "string (required)",
  "topicId": "string (optional — grounds the answer in a topic)",
  "curriculumId": "string (optional — grounds the answer in a curriculum)",
  "transcript": [{ "role": "user" | "assistant", "text": "string" }]  // optional
}
```

Response `200`:

```json
{
  "reply": "string",
  "suggestedSubtopics": [{ "title": "string", "rationale": "string" }],  // optional
  "citations": ["https://…"]  // optional
}
```

`404 { "error": "not_found" }` when the given `topicId`/`curriculumId` does not
resolve; `400 { "error": "invalid_input" }` on a bad body. `suggestedSubtopics`
is present only when the agent chose to propose sub-topics (and a curriculum was
in view); `citations` only when the agent opted into web search. Both are data
for the FE to act on with an explicit learner click — the agent never writes.

## Decisions made

- **Tool mechanism**: the agent builds tools dynamically from `requestContext`
  (`qaChatDeps`), exactly like `structure-editor.agent.ts` — never Mastra's
  `clientTools`.
- **Sub-topic suggestions are generated by the model, not a nested LLM call.**
  The agent proposes `{ title, rationale }[]` as tool arguments; `suggestSubtopics`
  validates them against the course's existing topic titles (read via
  `getModuleProgressSnapshots`), rejects duplicates and the no-curriculum case,
  and records the proposal into the per-turn in-memory `state`. This mirrors the
  existing `suggestSplitIntoCourses` precedent and means no extra cost mechanism.
- **Web search reuses `webSearch()`** from `probe-grounding.ts`; the tool's
  `execute` filters every returned citation through `isSafeSourceUrl` and
  dedupes. It is opt-in per question — the service never calls `webSearch`
  directly, only wires it into the tool deps.
- **Model tier** follows the existing cascade with no new mechanism: the agent
  uses `dynamicResolvedModel` (reads `curriculumId` off `requestContext`), and
  the `searchWeb` dep passes `{ curriculumId }` into `webSearch`'s scope so the
  paid call resolves the same tier.
- **Tool-step bound** of `maxSteps: 4` bounds the tool loop (cost/runaway-loop
  guard).
- All LLM calls go through `generate-with-retry.ts`; the agent is registered in
  `mastra.ts`'s `AGENT_KEYS` and agents map (no silent tracing gap).
