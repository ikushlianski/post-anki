## To review / clarify (not blockers, flagged for awareness)

1. **#84/#86 dependency check — concluded "not blocking," reasoning here for verification.** #90's
   issue body names #85/#86 as a conceptual dependency ("needs the mastery-overlay-on-static-
   taxonomy model those items are building"). That model is built (confirmed by PM triage). The
   one thing left open on #84 is Decision #2 there — which subject receives the taxonomy in
   *production*. This plan never needs to know that: every function takes `subjectId` as a
   parameter, mirroring `seed-domain-taxonomy.ts`'s own deliberate parameterization for the exact
   same reason (`spec.md`'s "Precedents" #4). #86 (visual knowledge map) is a rendering-only epic
   this feature never touches. **If this reasoning is wrong** — if Ilya's eventual #84 answer
   changes something structural about how domain nodes are scoped, not just which subject id is
   "the" production one — this plan's `subjectId`-parameterized design should still hold, but flag
   it for a second look before merging.
2. **Widen is scoped to root-level (15 "domains") only, not every sibling pair at every tree
   depth** (`spec.md` Decision 9). This is a literal reading of the issue's own "sibling domain"
   language and `it-taxonomy.yaml`'s `domains:` vocabulary, chosen specifically because it keeps
   deepen and widen non-overlapping. A broader reading (any sibling pair, at any depth, counts as
   "widen") is equally defensible from the issue text alone — if that's the intended scope, this
   is a parametrization of `computeWidenCandidates`, not a rewrite.
3. **Accept always creates a brand-new curriculum; it never extends an existing one in place**,
   despite the issue's literal "creates/extends a course" wording (`spec.md` Decision 3). Verified
   by grep that no existing mechanism can inject a bare topic name into an already-`ready`
   curriculum's structure — `mergeSourcesIntoCurriculum` needs real source drafts, and the only
   other non-URL research trigger (`submitStructureTurn`'s `researchGapLabels`) is gated to
   `status === "shaping_structure"` only. Worth a second look if there's course-extension UX
   planned elsewhere that this should hook into instead.
4. **No LLM call anywhere in this feature** (`spec.md` Decision 1) — the issue's own wording
   already specifies a deterministic rule, so this plan treats it as one rather than routing it
   through an agent the way `domain_priority_suggestions` does. Cheaper, deterministic, and
   directly testable, but it does mean reason text is templated rather than freely generated —
   flag if a more varied/conversational reason string is actually wanted.
