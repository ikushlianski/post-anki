## The fix (the one real code change this ticket made)

`verification-repo/projects/post-anki/post-anki/mock-openrouter/responses.ts` —
`buildPhraseBatchStub` now takes `userText: string`, parses the `Pack: <X>` line the app's real
`buildPhraseBatchPrompt` already embeds in every generation prompt, and returns pack-specific
themed content via a `PHRASE_BATCH_PACK_BUILDERS` map (one builder per pack: General, StandupUpdates,
CodeReview, IncidentPostmortems, GivingFeedback). Unrecognized/unparseable pack values throw
synchronously — no wildcard fallback. General's builder is byte-for-byte the pre-existing stub
text. The `phrase-batch-generate` responder's `content` callback now passes `ctx.userText` through.

## Deviations from the plan, discovered while writing the tests

1. **UI assertions cover the first 5 rendered phrases, not all 10.** `batch-practice.tsx` renders
   only `chunkSize` (default 5) phrase cards at a time — `phrase-card-5..9`/`phrase-russian-5..9`
   don't exist in the DOM until the "Answer 10 at a time" toggle is clicked, and that toggle has no
   `data-testid`. Adding one would be an application-code change, which this ticket's plan
   explicitly scoped to zero. Rather than break the framework's testid-only-selector rule (text/role
   selectors are reserved for genuinely invariant elements like browser dialogs) to reach the
   toggle, the UI assertion was scoped to the 5 visible cards; the `countWhere` persistence-layer
   assertion (which the plan itself calls "the stronger of the two claims") still covers the full
   10-row claim per batch.
2. **DB count assertions use "≥10 and a multiple of 10" / monotonic-growth, not a fixed "=== 10".**
   `usePracticeBatch` prefetches the next batch for the current level:pack the instant a batch
   renders ready (existing, intentional app behavior — the same race the
   `retry-storm-guard-bounds-failed-generate` test's own comments already document). The mock's
   fixed 400ms completion delay means that prefetch's own 10-row write can land before or after a
   given assertion runs, depending on real elapsed time — an exact `=== 10` count is flaky by
   construction once more than one UI action separates a batch's render from the DB read. The tests
   assert what the scenario actually claims instead: at least one full batch was written under the
   right pack, in multiples of BATCH_SIZE, and a pack switch never decreases another pack's count
   (S3's core negative claim). Confirmed stable across 3 repeated runs.
