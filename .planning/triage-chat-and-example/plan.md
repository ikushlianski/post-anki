# Triage: Chat about this + AI example

Planned 2026-10-28. Plan only, no code changed. Companion files: spec.md (contracts, decisions, rules), scenarios.md (test list).

## Business summary

While triaging suggested cards, the learner gets two more choices besides keep and drop.

1. Chat about this (swipe down on a phone, a button or the C key on web). The underlying knowledge item (the fact, not the card) leaves the triage queue without being approved or rejected and lands in a special deck called Inbox. From the Inbox the learner opens the existing "Chat about this" tutor to ask for specifics. Each Inbox item can later go back to triage or be discarded.
2. AI example (swipe up, a button or the E key). The AI writes one short example for the card and it appears under the answer. The learner stays on the same card and still decides keep or drop. One tap on Undo restores the previous example. A new example can be requested again, up to 5 per item.

Neither choice teaches the card-quality feedback loop (style notes): putting something in the Inbox is not a verdict on the card.

Name clash to resolve: the product already calls the triage list "Inbox" in places (iOS code comments and docs, sidebar test wording, a "Knowledge Inbox" label in the iOS item chat). The iOS tab and the web sidebar link are already labelled "Triage" and "Knowledge triage", so the user-facing name "Inbox" is free. Default taken: the new deck is called Inbox; internal code never uses "inbox" for the triage queue in new code, and the stale "Knowledge Inbox" wording in iOS item chat is renamed in Part 3.

## Architecture changes (ownership, boundaries, contracts)

- Knowledge item (knowledge bit) gets a fourth lifecycle state `inbox` beside pending, approved, rejected, superseded. Inbox is a state of the item, not a subject and not a new table.
- The example already exists: it is the item's `background` text, shared by all its cards, shown in triage and under the answer in study. AI only fills that field and records that it did (timestamp plus a per-item counter for the cap).
- Item chat is reused unchanged except its gate: today only approved items can be chatted with; Inbox items are allowed too.
- AI example is one new small agent on the existing "knowledge item model" (the admin-chosen cheap model used by card generators), no tools, structured output, covered by mock mode and the daily spend guard.
- Contract additions are additive: new endpoints, new optional fields, one migration (0126, additive columns only).
- iOS stays online-only for triage (it is today). No local-first or offline queue is added.

## Order of work

Part 1 backend, then Part 2 web, then Part 3 iOS (iOS decodes the Part 1 shapes in spec.md). Each part is a separate implementation dispatch; planning and implementation stay in different agents.

### Part 1: Backend and shared contract
1. Migration 0126 and schema: three columns on the knowledge items table (inbox time, AI example time, AI example count) plus a partial index for the Inbox list. Journal entry and snapshot generated by the repo's migrate script, never pushed directly.
2. Shared package: add `inbox` to the approval-state enum, add the Inbox/example Zod shapes (spec.md section "Contracts"), add `inboxCount` to the pending count response, add optional `exampleAiGeneratedAt` to the pending review bit.
3. Inbox transitions in one repo: move pending to inbox, return inbox to pending, discard inbox to rejected (no verdict recorded). All lock the row, are idempotent, and refuse other states with 409.
4. Inbox list endpoint, newest first, with subject name and card count.
5. Chat gate: item chat accepts approved and inbox.
6. AI example: agent, prompt builder (untrusted-text escaping), service (state check, cap check, overwrite rule, write), controller, route. A human edit of the example clears the AI marker.
7. Pending count endpoint also returns inboxCount.
8. Tests: unit (prompt escaping, service rules, controller), integration (transitions, concurrency, cap), mock-mode run.
Exit: `npx tsc --noEmit`, lint, vitest for shared and api, migration applied on a dev lane.

### Part 2: Web
1. Triage focus screen: two new buttons (Chat about this, AI example) beside Reject/Approve, keys C and E, touch-only vertical drag with edge rules, live-region announcements.
2. Decision handling: inboxed items leave the queue, are never sent to the triage session record, show in the done screen as "N sent to Inbox", and are undoable with Z and the Undo button.

5. Tests per scenarios.md.

### Part 3: iOS
1. Package: decode new shapes, new API calls (move to inbox, return, discard, list, generate example), count field.
2. Triage card: vertical swipes with scroll-edge rule, two buttons in the action area, VoiceOver custom actions, reduce-motion behaviour.
3. Model: inbox decision type kept out of the server triage session record, undo support, example generation with undo.
4. Inbox screen reachable from the Triage tab summary; reuses the existing item chat screen; rename the stale "Knowledge Inbox" text.
5. Offline: both actions need the network and fail with a clear message; nothing is queued.
6. Package tests, smoke tests with the fake server, fixtures.

## Risks and open points

- Inbox items still get cards generated by the background scans (cost: same as any item). Accepted: they are ready if the learner sends the item back to triage.
- Re-extracting a source supersedes only pending items, so Inbox items survive and could be duplicated by the new extraction. Accepted for now; duplicate detection already runs on pending items.
- Chat transcripts are not saved (existing item chat is stateless). If the learner wants history in the Inbox, that is a separate feature.
- Sorting an Inbox item directly into a subject is not offered: subject lives on the source, so a move would drag along sibling items. Subject sorting stays available after approval (existing move).
- Verify before building: discard without a verdict leaves the item's pending feedback row open; confirm no report counts open feedback rows as "undecided".
