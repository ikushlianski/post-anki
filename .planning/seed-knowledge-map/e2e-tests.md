## Infra additions this run made (not application code)

- `apps/api/vitest.integration.config.ts` + `apps/api/package.json`'s new `test:integration`
  script — this project's `vitest.config.ts` `exclude`s every `*.integration.test.ts` file from the
  fast default sweep, and this vitest version's CLI `--exclude` flag is **additive-only** (confirmed
  empirically — it appends to, never replaces, the config's exclude list), so there was previously
  no working way to run an individual integration test file directly (`npx vitest run
  apps/api/src/db/migrations.integration.test.ts` — the pre-existing precedent file — also failed
  with "No test files found" before this fix). Real command going forward:
  `npx vitest run --config vitest.integration.config.ts <path>` or `npm run test:integration --
  <path>`, from `apps/api/`.
- `verification-repo/projects/post-anki/post-anki/db/pg.ts` gained a generic `insertRow(table,
  values)` helper (same safe-identifier validation as the existing `countWhere`/`getRow`), needed
  by the new back-door seed fixture — no other feature's seed does a raw insert yet, so this is a
  new but natural extension of the existing generic-table-helper module, not a one-off.

## What is NOT covered yet (flag for the human)

- Nothing scenario-level. All 9 scenarios (S1-S9) have a test. Every e2e scenario (S3, S4, S5, S7,
  S8, S9) was run against a live worktree stack and confirmed to fail for the expected reason
  (`relation "domain_nodes" does not exist`), not a typo or environment problem.
- **S8's fixture deviates from scenarios.md's literal wording** — see the file-level comment in
  `studied-node-rollup-visible-on-ancestors.test.ts` for the full reasoning. Short version:
  scenarios.md assumes an *untouched* (zero-topic) sibling node dilutes a parent's rollup average
  toward 0, but per SCENARIO 2's own precisely specified math (a node with zero topics contributes
  zero topics to a flattened parent average, not zero-maturity phantom topics), a genuinely empty
  sibling branch does not change the parent average at all — with only "Nuxt.js" as the diluting
  sibling in the shared fixture, Meta-frameworks/Frontend would read the *exact same* percent as the
  leaf, not "lower" as the scenario's Behavior block demands. Fixed by seeding one additional
  low-maturity (0) topic under "Nuxt.js" in S8's own fixture instance only (S7's separate subject
  keeps "Nuxt.js" genuinely untouched for its own claim), which produces real, correctly-computed
  dilution consistent with the deriver's actual rules.
