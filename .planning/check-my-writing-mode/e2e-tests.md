## New action + fixtures this run added

- `checkWriting({ page, subjectId, text })` — `verification-repo/.../features/practice/actions/check-writing.action.ts` — waits on the real `submitWritingCheck` server-function network response, then reads the rendered result back from the DOM.
- `isServerFnResponse()` / `decodeServerFnUrl()` — new shared helper,
  `verification-repo/.../projects/post-anki/post-anki/lib/server-fn-response.ts`. TanStack Start
  server functions POST to `/_serverFn/<base64>`, where the base64 segment decodes to
  `{ file, export }` naming the handler — the underlying REST call (`/subjects/:id/writing-checks`)
  happens server-side inside that handler and is never itself a browser-visible request. The plan's
  own wording ("the base64 `/_serverFn/`-marker technique, generalized from `submit-chunk.action.ts`'s
  existing `isGradeBatchResponse`") assumed a generalizable helper already existed — it didn't
  (grep confirmed no `isGradeBatchResponse` anywhere in this repo; `answerAndSubmitChunk` actually
  waits on DOM visibility, not network). The `/_serverFn/` mechanism itself is real and now
  confirmed empirically (decoded a live trace's network log), so this run built the helper fresh
  rather than reusing a nonexistent one.
- `MOCK_WRITING_CHECK_SLACK_MESSAGE` / `MOCK_WRITING_CHECK_STIFF_EMAIL` + `buildWritingCheckStub()` — new responder in `verification-repo/.../mock-openrouter/responses.ts`, matched on `schemaProps.includes('nativeAlternatives') && !schemaProps.includes('gradedAnswers')`, content selected by matching the submitted text inside `ctx.userText` (no enqueue/queue mechanism exists in this mock).

Deviation from the plan's literal file split: the plan's `state-fixtures.md` proposed the two fixture
objects living under `features/practice/fixtures/mock-data/`, separate from the mock-openrouter
responder. This project's actual convention (checked against `grade-batch`/`phrase-batch-generate`,
the two existing practice-feature responders) keeps stub content directly in
`mock-openrouter/responses.ts` as exported consts — `features/practice/fixtures/mock-data/index.ts`
holds only the `setupLanguagePracticeSubject` helper, no raw fixture data for any existing
responder. Followed the actual codebase convention rather than the plan's generic template wording.

## First red run (before implementation)

Captured by `git stash -u`-ing every implementation file (keeping the 3 test files + action +
fixture intact) and running the suite against that reverted state:
`bash e2e/scripts/run.sh -g "@check-my-writing-mode"`. All 3 failed for the right reason —
`notFoundError` on `__root__` (the new route didn't exist) and, once past that, a `120000ms` timeout
on `.fill()` against `check-writing-input` (the testid/page never existed either). Not a compile
error. The implementation was then restored (`git stash pop`) and the suite re-run.

## Two real bugs found and fixed during the first green attempt

1. **`checkWriting`'s existence check raced the page load.** The action used
   `input.count()` (a one-shot, non-waiting check) immediately after `page.goto()`. S3 passed on the
   very first attempt (it drives `check-writing-input` via `.fill()`, which auto-waits), while S1/S2
   both failed with `missing data-testid="check-writing-input"` — proving the route/testid were fine
   and the bug was in the action's own race-prone existence check. Fixed by switching to
   `input.waitFor({ state: 'visible' })`, matching this codebase's own established pattern
   (`openPracticePage`'s identical `waitFor`-then-catch shape).
2. **The network-response wait matched the wrong URL.** `page.waitForResponse` was matching on
   `res.url().includes('/writing-checks')` — the literal REST path. That path is never a
   browser-visible request for a TanStack Start server function; the browser only sees
   `POST /_serverFn/<base64>`. Confirmed by decoding a live trace's network log (see
   `lib/server-fn-response.ts`'s comment for the exact decoded payload). Fixed by matching on the
   decoded handler name (`submitWritingCheck_createServerFn_handler`) instead, and used the same
   matcher to fix S3's "no request fired while disabled" check, which had been vacuously true before
   (it could never have matched any real request, disabled or not).
