# Architecture: Schema for processed entries and manual knowledge items

## What changes structurally
The entry gains one user-owned timestamp (processed) set and cleared only by two explicit routes; no background job, status transition or regeneration touches it. Each knowledge item gains an origin (extracted or manual). Everything that attributes quality to a model is closed to manual items twice: the feedback writer never writes a row for them, and every reader (per-model counts, default-model evidence, reviewer memory, report view) filters them out, so a stray row cannot leak in.

## New infrastructure
None.

## Data model evolution
- Entry: `processed_at` timestamptz, null = open. No index (always read by entry id).
- Knowledge item: `origin` text not null default `extracted`, check constraint limits it to `extracted` or `manual`. No index (only used as a filter after a primary-key join).
- The feedback report view is replaced in the same migration with the same columns plus a filter that drops manual items.
- Feedback and extraction-grade tables, comparison tables and their views keep their shape.

## Failure modes
- Mark or reopen racing with a claim for extraction: one conditional update decides; a claim that wins makes the route answer 409, a route that wins leaves the claim unaffected.
- Old code writing a feedback row for a manual item during a rolling deploy: the readers exclude it anyway.
- Reader filter forgotten in a future query: the integration tests pin all current readers; new readers must reuse the shared exclusion.
- Extraction grade is per entry run and never about one item, so it needs no exclusion.

## Rollout
- Migration 0096 is generated by drizzle, never pushed. The coordinator applies it to the local Docker DB on 5562 after a backup; tests only use throwaway databases on the pet-projects lane (127.0.0.1:5999).
- Deploy order: migration first, then API (the API reads the new columns).

## Non-goals
- No automatic processed transition, no change to extraction status values.
- No route that creates a manual item, no web screens, no Processed section, no Reopen button (later todo items).
- No rename of tables, columns or kind values; no source container.
- Regeneration supersedes pending extracted items only; pending manual items stay.
- No new entry-list endpoint; the web reads processed from the pending-review payload.
- The sidebar count query ignores pending items of processed entries, so marking removes them from the badge and reopening restores them. The model-comparison data and the extraction grade are unchanged.

## Rollback note
The migration is additive: one nullable column and one defaulted, check-constrained column, plus a replaced view whose columns are unchanged. Rolling back the API alone is safe (old code ignores the new columns, and old readers that miss the filter only see extracted rows until manual items exist). A full rollback drops the check constraint and the two columns and restores the previous view definition from migration 0093 through a new migration; processed marks and manual origins are lost, so it is only done before manual items exist.
