# Spec: F-core — Anki review core

### Summary
Learners get a second way to review approved knowledge bits. They see a question, reveal the answer, and grade themselves Again, Hard, Good or Easy, the way Anki works, without typing and with no AI grading cost. The bit's own text and the tutor chat stay hidden until the answer is revealed, so recall isn't spoiled, and the whole session can be run from the keyboard. Every grade updates the same per-bit schedule the typed mode uses. It also leaves a permanent history entry that keeps a copy of the previous schedule, so later features (undo, daily new-card counts, leech detection) need no further migration.

### The ask
> Feature F-core. Plan only these four items:
> 1. Add Anki review mode: show answer, then self-grade Again/Hard/Good/Easy
> 3. Hide bit text above the question in Anki review mode
> 9. Keyboard shortcuts: Space reveals answer, 1-4 grade the card
> 20. Hide the chat panel until the answer is revealed
>
> Scope: F-core owns the first migration, which creates the append-only knowledge_bit_reviews table with a prev_schedule snapshot. It also owns: the new 4-grade schedule deriver; GET /knowledge-bits/review-cards and POST /knowledge-bits/reviews; the shared Zod contracts; the separate /knowledge/review route with its anki-review components, plus links between it and /knowledge/answer, and a sidebar entry.
>
> Do NOT plan any of these: the due-queue rule, learning steps, daily caps, undo, suspend/bury, the basic variant or the after-paste trigger. [...] Interval previews are a later item too, so keep the response shape forward-compatible but leave them out.

Binding architecture: `.planning/classic-anki-review/brief.md`. Row source: `.planning/classic-anki-review/breakdown.md` (F-core). Background: `.planning/anki-scenario-review/report.md`, `.planning/anki-scenario-review/ux-review.md`.

### Derivers
| Deriver | Inputs | Output | Scenarios covered |
|---|---|---|---|
| `deriveGradeSchedule` in `apps/api/src/knowledge-bit/knowledge-bit-grade-schedule.ts` | prior state `{easeFactor, intervalDays}` or `null` (never reviewed), `grade` (again/hard/good/easy), `now` | `{easeFactor, intervalDays, dueAt, phase: "review", wasNew}` | SCENARIO 2, SCENARIO 8 |
| `ankiReviewKeyAction` in `apps/web/src/knowledge-bit/anki-review-keyboard.ts` | key event facts `{key, repeat, ctrlKey, metaKey, altKey, targetIsEditable}`, screen facts `{hasCard, revealed, busy}` | `{type: "reveal"}`, `{type: "grade", grade}` or `null` | SCENARIO 5 |

Grade rule, all clamped to ease 1.3–3.0 and interval 1–180 days. The interval uses the ease from before the grade, and the ease adjustment is applied afterwards.
- Never reviewed (`null`): again, hard and good give 1 day, easy gives 4 days. Ease stays at the 2.5 default. `wasNew = true`.
- Reviewed: again gives 1 day with ease −0.20. Hard gives `max(I,1) × 1.2` with ease −0.15 and no 14-day cap. Good gives `max(I,1) × E` with ease unchanged. Easy gives `max(I,1) × E × 1.3` with ease +0.15.
- `dueAt = now + intervalDays × 24h`. `computeNextSchedule` in `apps/api/src/knowledge-bit/knowledge-bit-schedule.repo.ts:24` is not touched.

### Contracts (`packages/shared/src/knowledge-bit-review.ts`, Zod)
- `reviewGradeSchema = z.enum(["again","hard","good","easy"])`. `cardPhaseSchema = z.enum(["new","learning","review","relearning"])`. The enum is the brief's full one, but F-core emits only `new` and `review`.
- `reviewCardsQuerySchema`: `limit` (coerced int, 1–50, default 10) plus optional non-empty `tagId`, `topicId` and `knowledgeBitId`. Unknown keys such as a future `tz` are stripped, not rejected.
- `reviewCardSchema`: `{variantId, knowledgeBitId, kind: knowledgeBitQuestionVariantKindSchema, prompt, answer, background: string|null, phase}`. It deliberately has no bit-body field.
- `reviewCardsResponseSchema`: `{cards: reviewCard[]}`. It is an object envelope, so `counts`, `newRemainingToday`, `nextDueAt` and `intervalPreview` can be added later without breaking clients.
- `recordReviewInputSchema`: `{variantId: string.min(1), grade, durationMs?: int 0–86_400_000}`.
- `recordReviewResultSchema`: `{reviewId, knowledgeBitId, phase, dueAt: ISO string, intervalDays}`. `lapses`, `leech` and `suspended` are added later.
- Endpoints:
  - `GET /knowledge-bits/review-cards`: 200 `reviewCardsResponse`, or 400 `invalid_input`.
  - `POST /knowledge-bits/reviews`: 201 `recordReviewResult`, 400 `invalid_input`, 404 `variant_not_found` or 403 `not_approved`. These mirror `apps/api/src/knowledge-bit/grade-knowledge-bit-variant-answer.controller.ts:27-29`.

### Data model changes
New table `knowledge_bit_reviews` (Drizzle `knowledgeBitReviews`), append-only, no FKs (neighbouring-table convention, `apps/api/src/db/schema.ts:1177`):

| Column | Type | Notes |
|---|---|---|
| id | text PK | `newId("kbreview")` |
| knowledge_bit_id | text not null | |
| variant_id | text not null | |
| grade | text not null | again/hard/good/easy, validated by Zod (no DB check, as `approval_state`) |
| was_new | boolean not null | true when no schedule row existed |
| duration_ms | integer null | |
| prev_schedule | jsonb null | `{easeFactor, intervalDays, dueAt, lastReviewedAt, reviewCount}`, ISO timestamps; null when was_new |
| reviewed_at | timestamptz not null default now() | |
| undone_at | timestamptz null | unused until undo |

Indexes are `(knowledge_bit_id, reviewed_at)` and `(variant_id)`. Generate with `npm run db:generate:api`, then apply with `npm run db:migrate:api` (that is `apps/api/scripts/migrate.ts`) with `DATABASE_URL` exported to the local dev DB. Never push. Later columns (phase, learning_step, lapses, suspended_at, buried_until) join the snapshot once they exist, and undo must default any key that is missing from an older snapshot.

### Risk & rollout
- Blast radius: the shared schedule row. A bug in the new upsert helper could corrupt the schedules typed mode reads. The integration tests cover it, and the existing typed exports stay byte-identical.
- Interim queue behaviour until F-queue lands: no due filtering, and two variants of one bit can arrive in the same batch. A small deck therefore cycles, and sibling variants can both be graded, which compounds the interval. This is the accepted state; F-queue owns the fix.
- The migration must be applied against a local DB only. `apps/api/.env`'s `DATABASE_URL` points at production, and the migrate script refuses non-local hosts outside CI (`apps/api/scripts/migrate.ts:15-38`).
- Deploy ordering and rollback: see architecture.md "Failure modes" and "Rollout". Standard deploy, and CI migrates before the API deploys (`.github/workflows/deploy.yml:206`).

### Phase 3 — resilience and infra-security pass
- **Auth:** both endpoints go through the existing `authorized()` gate (`apps/api/src/api-server.ts:280-306`), with no new public route. The route test asserts a 401 without a bearer token.
- **Input:** Zod covers the body and the query. `limit` is capped at 50 (the typed controller is uncapped and left unchanged). `durationMs` is bounded, the grade is an enum, and ids reach SQL only through Drizzle parameters. Body size is capped by `readJsonBody` (`apps/api/src/shared/http.ts:4`).
- **Data exposure:** answers are returned only by the new endpoint. The bit body is never selected. The typed endpoint keeps omitting the answer (`apps/api/src/knowledge-bit/knowledge-bit-question-variant.repo.ts:107-114`). The new table is not synced to clients, because Electric exposure is registry-based (`apps/api/src/electric/electric-shape-registry.ts`) and it is not registered.
- **Untrusted content:** prompts, answers and backgrounds are LLM output derived from pasted text. They are rendered as React text only, never as HTML.
- **Cost and loops:** the grade path makes zero LLM calls. The chat panel is unchanged but mounts later. Refetch happens only on a learner action. Mutations never auto-retry.
- **Concurrency:** writes run under a per-bit advisory lock shared with typed grading (`apps/api/src/shared/merge-lock.ts:58`), with the schedule upsert and the history insert in one transaction. Lock waits are bounded by the pool's connection timeout (`apps/api/src/db/client.ts`).
- **Idempotency:** the client ignores grade input while a grade is in flight and ignores key auto-repeat. There is no server idempotency key, because the brief fixes the contract. A double grade after a lost response is recoverable by the later undo feature.
- **Infra and secrets:** no new resources, no secrets, and no Cloud Run change.
