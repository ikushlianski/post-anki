**E2E tests (S1/S2)** — run via

the local e2e Postgres, migrates, boots the e2e API/web against THIS worktree's source per

unrelated environmental problem (see memory note below); after resetting the local e2e DB, both

```
✘ @curriculum-merge.S1 — ActionFailure: missing data-testid="curriculum-merge-button-<id>"
  (action: mergeCurriculum)
✘ @curriculum-merge.S2 — ActionFailure: missing data-testid="curriculum-merge-button-<id>"
  (action: openCurriculumMergePicker)
```

Both fail at the exact point the merge feature doesn't exist yet: the "Merge into…" control's
`curriculum-merge-button-${id}` testid is not present in the DOM. Every step before that —
subject/curriculum creation, the approve-sources/confirm-structure poll to `ready`, and (on the
successful retry) the tag-picker assignment — completed correctly, proving the failure is scoped to
the missing feature, not to test setup.

**Environmental note, worth recording in `docs/memories/`:** `e2e/docker-compose.yml`'s Postgres
container uses `tmpfs` for its data directory (intentionally ephemeral per-container-lifetime), but
the container itself (`post-anki-e2e-db`) had been left running continuously across many past local
sessions without ever being stopped — so `docker compose up -d` kept no-op'ing against the same
long-lived container instead of getting a fresh one, and its tmpfs had accumulated 848 leftover
`subjects` rows (and a large multiple of that in curricula/modules) from months of prior ad hoc e2e
runs. Rendering the home page with that much data made a first attempt at S1/S2 fail with a 120s
timeout waiting for `study-technology-name-input` — not a testid problem, a page-weight problem: the
click landed, but hydration/re-render of an ~800-subject list didn't settle inside the timeout, which
would have been misdiagnosed as "the feature is missing" for the wrong reason. Fix: `docker compose
-f e2e/docker-compose.yml down && docker compose -f e2e/docker-compose.yml up -d` (a real container
restart, not just `up -d` against an already-running one) actually clears the tmpfs, then re-run
`db:migrate`. Re-running after that reset both tests completed in under 7 seconds and failed at the
correct, feature-scoped assertion. Recommend adding this as its own dated entry under
`projects/post-anki/post-anki/docs/memories/` so the next session doesn't re-diagnose the same false
timeout as a hydration bug.

## Deviation from state-fixtures.md, found while writing S1 (report to the human)

`state-fixtures.md`'s S1 setup names `direct request.post(/curricula/:sourceId/sources)` as the
mechanism for adding the scenery "extra source" on the source curriculum. Reading
`handleAddSources` (`apps/api/src/curriculum/curriculum.controller.ts`) while writing the test
showed that route, once a curriculum is already `status: 'ready'`, does NOT just insert a row — it
sets the curriculum to `status: 'curating'` and dispatches an async re-generation pipeline
(`mergeSourcesIntoCurriculum`, `curriculum-parse.orchestrator.ts`) against the mocked LLM, which
would race the test's own subsequent merge call and make the test's timing non-deterministic. The
test instead inserts the `sources` row directly via SQL (`insertRow('sources', {...})`), which
produces the same row the scenario needs to exist without the unrelated async side effect. This is
a plan-vs-codebase inconsistency, not a scope change — the row itself, its columns, and what the
merge does with it are unchanged from spec.md/state-fixtures.md's intent.
