# Research: Grouping, the current-subject label and the next-subject announcement already exist in the API and the iOS DueReviewModel. Should the work cover only the missing surface (Mac, web or Expo), or re-verify and change the existing iOS behaviour? I did not check whether the Today/all-subjects scope reaches this grouped path.

## Facts
- Fact: The API review-cards handler passes tag, topic, card and subject filters to the queue (all optional), then always runs groupReviewCardsBySubject over the result. Grouping therefore applies to every scope, including an unscoped request. (source: apps/api/src/knowledge-bit/knowledge-bit-review.controller.ts:34)
- Fact: groupReviewCardsBySubject orders cards by the first appearance of each subjectId, keeps the original order within a group, and attaches a subjectPath label (null when there is no label). (source: apps/api/src/knowledge-bit/knowledge-bit-review-subject-groups.ts:5)
- Fact: iOS Today entry: DueTodayCard opens DueReviewScreen() with no scope. DueReviewModel.load then sends subjectId: scope?.subjectId, which is nil, to the API. So in the online path the all-subjects Today scope does reach the grouped endpoint. (source: apps/ios/Sources/PostAnkiIOS/DueTodayCard.swift:9)
- Fact: DueReviewModel.load calls APIClient.reviewCards and then queues the cards in server order, with no re-sorting on the client. (source: apps/ios/Sources/Shared/DueReviewModel+Loading.swift:43)
- Fact: The iOS model already exposes currentSubjectPath (the current-subject label) and groupAnnouncement. The announcement shows only when the subject changes and the card is not revealed. It uses the cards left in the group plus the overall remaining count. (source: apps/ios/Sources/Shared/due-review-progress.swift:26)
- Fact: ReviewSubjectGroups builds the announcement text 'Next subject: <path> · N cards here, M cards left in total'. cardsLeft counts the current card plus the following queue cards with the same path. (source: apps/ios/Sources/Shared/due-review-subject-groups.swift:12)
- Fact: DueReviewCardBody renders the announcement, and DueReviewModel records previousSubjectPath when it moves to the next card. (source: apps/ios/Sources/Shared/DueReviewCardBody.swift:44)
- Fact: Tests exist for the API grouping and for the iOS announcement text, and the iOS ReviewCard decoder has a subjectPath test. (source: apps/api/src/knowledge-bit/knowledge-bit-review-subject-groups.test.ts)
- Fact: The web client's review API file references only a subjectId query key. It has no subjectPath, grouping or announcement code, so web has none of the surface. (source: apps/web/src/knowledge-bit/anki-review.api.ts:55)
- Fact: The Mac app uses DueReviewModel (MacDueReviewView, MacDecideView). It shares the Shared model, so the label and announcement logic is available there. Whether Mac renders them was not verified. (source: apps/ios/Sources/PostAnkiMac/MacDueReviewView.swift)
- Fact: The mobile app has an AGENTS.md carrying the rule to read the versioned Expo docs before writing code. It is the only mobile file found that touches this feature. A mobile review screen using this endpoint was not found. (source: apps/mobile/AGENTS.md)

## Open questions
- Open question: Offline pack path: when ReviewPackSync is offline, load() calls loadFromPack() before the API. DueReviewModel+OfflinePack.swift has no subject references, and the pack repo only selects subjectId and cardSubjectId. It is unconfirmed that pack cards carry subjectPath or are grouped, so Today may show no label or announcement offline.
- Open question: Whether Mac views (MacDueReviewView) and the Expo mobile app display currentSubjectPath and groupAnnouncement was not verified. The Mac view uses the shared model; the Expo app was not found to have a review screen.
- Open question: Counts differ from the ticket: the announcement gives the count left in the group plus the overall total, and the window is limited to ReviewCardWindow.target cards. Groups beyond the loaded window could be undercounted in 'cards left here'. Not verified.
- Open question: Product decision: extend only the missing surfaces (Mac, web, Expo, offline) or also change the existing iOS behaviour. The code supports the first as the default (iOS online already meets the ticket), but the stakeholder has not confirmed it.
