A database index is a separate data structure, usually a B-tree, that lets the engine find rows without scanning the whole table. A lookup on an indexed column takes logarithmic time, while a lookup on an unindexed column forces a sequential scan whose cost grows linearly with the number of rows. Indexes are not free, however. Every insert, update or delete must also modify each index that covers the changed columns, so a table with many indexes writes more slowly. Indexes also consume disk space and memory, which competes with the cache that holds hot table pages. For this reason, write-heavy tables such as event logs are usually kept with very few indexes, while read-heavy tables such as product catalogues can afford many. A composite index on columns (a, b) helps queries that filter on a alone or on a and b together, but not queries that filter on b alone, because the tree is sorted first by a and only then by b. Before adding an index, measure the real query plan and confirm the planner actually uses it.
